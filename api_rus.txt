Спецификация API рыночных данных

1. Открытие сервиса

Клиентское приложение должно установить WebSocket-соединение с адресом, предоставленным поставщиком услуг. Сразу после установления соединения необходимо отправить запрос на открытие сервиса `open` [4.1.a].

В запросе передаётся уникальный идентификатор клиента `<session_id>`, предоставляемый поставщиком услуг. При успешном открытии сервиса сервер отправляет сообщение `init` [4.1.b], содержащее идентификатор клиента. Если открыть сервис не удалось, сервер возвращает сообщение `result` [4.1.c].

Если на сервере уже существует открытая сессия с тем же `<session_id>`, успешное открытие новой сессии приводит к закрытию предыдущей. Клиентское приложение, использовавшее предыдущую сессию, получает уведомление `finish` [4.1.d], после чего сервер закрывает его WebSocket-соединение.

2. Поддержание сессии

Для поддержания открытой сессии клиент должен периодически отправлять серверу запрос `ping` [4.2]. Такой запрос продлевает срок действия сессии и позволяет выявлять возможные задержки связи между клиентом и сервером.

Обязательный параметр запроса — идентификатор клиента `<session_id>`. Дополнительно можно передать идентификатор запроса `<ping_id>`; этот параметр необязателен.

3. Подписка на рыночные данные

Состав доступных рыночных данных определяется поставщиком услуг. Поддерживаются три типа сообщений [5]:

- Котировка (спред) — текущие цены спроса (`bid`) и предложения (`ask`) [5.1].
- Сделка — цена и объём сделки [5.3].
- Последняя цена (`Last Price`) — усреднённое значение спреда с дополнительными параметрами изменения цены относительно закрытия предыдущей торговой сессии по инструменту [5.2].

Каждое сообщение с рыночными данными содержит тикер инструмента и временную метку UTC.

Для управления подпиской клиент отправляет запрос на замену списка подписанных инструментов [4.3] или на добавление инструментов в существующий список [4.4]. Оба запроса содержат идентификатор клиента `<session_id>` и список тикеров.

3.1. Замена списка подписки

Запрос `update` [4.3] заменяет текущий список подписки переданным списком тикеров. Сервер отменяет подписку на инструменты, отсутствующие в новом списке, и оформляет подписку на инструменты, которых ранее в подписке не было.

Таким образом, для изменения состава подписки достаточно одного запроса: отдельно отменять подписку на исключённые инструменты не требуется.

Чтобы отменить все подписки, необходимо отправить запрос `update` с пустым списком тикеров.

3.2. Добавление инструментов в список подписки

Запрос `add` [4.4] добавляет указанные инструменты в текущий список подписки. Если подписка на инструмент уже существует, она сохраняется без изменений; в противном случае инструмент добавляется в список.

В отличие от `update`, запрос `add` не отменяет подписку на инструменты, отсутствующие в переданном списке. Запрос `add` с пустым списком тикеров не изменяет текущую подписку.

4. Форматы служебных сообщений

4.1. Открытие сервиса

4.1.a. Запрос на открытие сервиса:

{ "msg": "open", "sid": "<session_id>" }

4.1.b. Ответ при успешном открытии сервиса:

{ "msg": "init", "sid": "<session_id>" }

4.1.c. Ответ при ошибке открытия сервиса:

{ "msg": "result", "respCode": "<код_ошибки>", "message": "<описание_ошибки>" }

4.1.d. Уведомление о закрытии предыдущей сессии после открытия новой:

{ "msg": "finish", "sid": "<session_id>" }

4.2. Поддержание сессии (ping)

Запрос:

{ "msg": "ping", "sid": "<session_id>", "pid": "<ping_id>" }

Ответ сервера:

{ "msg": "ping", "sid": "<session_id>", "pid": "<ping_id>" }

Параметр `pid` необязателен.

4.3. Замена списка подписки

Запрос:

{ "msg": "update", "sid": "<session_id>", "tickers": ["ticker1", "ticker2", "tickerN"] }

4.4. Добавление инструментов в список подписки

Запрос:

{ "msg": "add", "sid": "<session_id>", "tickers": ["ticker1", "ticker2", "tickerN"] }

5. Форматы сообщений с рыночными данными

5.1. Котировка (Quote)

{
  "msg": "quote",
  "ticker": "<ticker>",
  "bid": "<bid_price>",
  "ask": "<ask_price>",
  "utcdt": "<dd-MM-yyyy HH:mm:ss.ffffff>"
}

5.2. Последняя цена (Last Price)

{
  "msg": "lastprice",
  "ticker": "<ticker>",
  "last": "<last_price>",
  "netchange": "<netchange>",
  "netchangepers": "<netchangepercent>%",
  "utcdt": "<dd-MM-yyyy HH:mm:ss.ffffff>"
}

5.3. Сделка (Trade)

{
  "msg": "trade",
  "ticker": "<ticker>",
  "price": "<trade_price>",
  "size": "<trade_size>",
  "utcdt": "<dd-MM-yyyy HH:mm:ss.ffffff>"
}

6. Коды ответов сервера (сообщение result)

VALUE_RESP_SUCCESS = 0

Запрос успешно обработан.

VALUE_RESP_INVPARAM = 1

Запрос содержит недопустимый параметр. В поле `message` сервер указывает имя параметра, вызвавшего ошибку.

VALUE_RESP_FORBIDDEN = 4

Выполнение запроса запрещено текущей конфигурацией сервера либо идентификатор клиента заблокирован.

VALUE_RESP_REJECTED = 7

Запрос клиента отклонён. Причина отказа указывается в поле `message`.

Код ответа передаётся в поле `respCode` в виде строки (например, "0" или "1").

7. Запрос последних рыночных данных

API позволяет получить последние доступные рыночные данные по отдельному запросу. Ответ содержит данные по инструментам, тикеры которых указаны в запросе. Данные предоставляются только по инструментам, к которым у клиента есть доступ.

Эта возможность предоставляется как отдельная услуга. Для её подключения необходимо обратиться в службу поддержки.

7.1. Формат запроса

Запрос отправляется по протоколу HTTP на адрес, предоставляемый после подключения услуги.

Метод HTTP: GET

Формат запроса:

https://<адрес>?sid=<идентификатор>&tickers=<список_тикеров>

Параметры:

- `sid` — уникальный строковый идентификатор клиента, предоставляемый службой поддержки.
- `tickers` — список тикеров инструментов, разделённых точкой с запятой (`;`).

Пример:

https://<адрес>?sid=3mx7mt7&tickers=EURUSD;BTCUSD

7.2. Успешное выполнение запроса

При успешной обработке запроса сервер возвращает сообщение `result` со строковым кодом `respCode`, равным "0".

Поле `message` содержит непосредственно JSON-массив с последними доступными рыночными данными по запрошенным инструментам, а не строку с сериализованным JSON.

Пример ответа (значения условные):

{
  "msg": "result",
  "respCode": "0",
  "message": [
    {
      "msg": "quote",
      "ticker": "EURUSD",
      "bid": "1.1750",
      "ask": "1.1752",
      "utcdt": "26-10-2026 14:30:15.123456"
    },
    {
      "msg": "lastprice",
      "ticker": "BTCUSD",
      "last": "68000",
      "netchange": "1250",
      "netchangepers": "1.87%",
      "utcdt": "26-10-2026 14:30:15.123456"
    }
  ]
}

Каждый элемент массива представляет собой сообщение одного из типов, описанных в разделе 5.

Если инструмент не существует, тикер указан неверно или у клиента нет доступа к инструменту, данные по нему в ответ не включаются.

7.3. Ошибка выполнения запроса

Если запрос не удалось выполнить, сервер возвращает сообщение `result` с соответствующим кодом ошибки.

Формат ответа:

{
  "msg": "result",
  "respCode": "<код_ошибки>",
  "message": "<описание_ошибки>"
}

Поля ответа:

- `respCode` — строковый код ошибки из раздела 6.
- `message` — текстовое описание причины ошибки в соответствии с разделом 6.

Таким образом, тип поля `message` зависит от результата запроса: при успешном выполнении оно содержит JSON-массив, а при ошибке — строку с описанием ошибки.
